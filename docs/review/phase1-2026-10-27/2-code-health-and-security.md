### New findings from this revision

### C10. `api.username_availability` can be probed without limit by anyone (Low)
- What: the function is callable by `anon`, has no per-caller throttle, and tells whether a username exists (`taken`) even though public boards mask usernames for anonymous visitors.
- Where: supabase/migrations/20260720081817_identity_null_validation.sql (final definition; granted to anon in 20260720075453_identity_domain.sql); used by src/backend/identity/supabase-repositories.ts:69.
- Why it matters to fans: an outsider can test whether a particular person's chosen handle has an account (for example a known player or a rival manager). It gives no email, name or id, and handles are meant to be public inside the app, so the harm is small.
- Attack path: script POSTs `/rest/v1/rpc/username_availability` with a list of guessed handles using only the public publishable key; each reply says taken or free. Volume is limited only by the platform's generic request limits, which I cannot see; I did not test it.
- Severity: Low. Effort: S (return the same answer for taken and reserved to anonymous callers, or throttle by IP at the edge).

### C11. Sign-up has no CAPTCHA in the code; fake accounts could enter prize challenges (Medium for prizes, Low otherwise)
- What: nothing in the app asks for a CAPTCHA token. `supabase/config.toml:213-216` has `[auth.captcha]` commented out. The sign-up call sends no `captchaToken`: src/services/auth-supabase.ts:434-441 (`this.auth.signUp({ email, password, options: { emailRedirectTo, data } })`). `grep -ri "captcha|turnstile|hcaptcha" src` returns nothing. The identity runbook says production needs "custom SMTP, production OAuth credentials, CAPTCHA/abuse settings required before go-live" (docs/backend/IDENTITY_AUTH_RUNBOOK.md:22) and "Hosted thresholds must be reviewed alongside SMTP/CAPTCHA settings before launch" (:174-175). I found no record that this was done.
- Strong inference about production: Supabase rejects any sign-up that lacks a captcha token once CAPTCHA is switched on in the dashboard. The client never sends one and sign-ups work in production, so CAPTCHA is almost certainly off there.
- Rate limits (local file only; production values are dashboard settings I cannot read): `email_sent = 2` per hour, `sign_in_sign_ups = 30` per 5 minutes per IP, `token_verifications = 30`, `token_refresh = 150`, `anonymous_users = 30` with anonymous sign-ins disabled (config.toml `[auth.rate_limit]` and `[auth]`, lines ~170-200). Email confirmation is required (`enable_confirmations = true`), which costs an attacker one real mailbox per account, but disposable-mail domains make that cheap. No device, phone or domain checks exist in the sign-up path that I found.
- Why it matters to fans: Fantasy has prizes (gameweek, monthly, season tiers, `app.fantasy_prize_winners`). Someone could create many accounts to take several slots in a sponsored challenge, to flood public leagues, or to vote in match polls; honest fans lose their place or the prize. Existing mitigations that reduce but do not remove it: winners must reach status `verified` or `paid` before they are shown (fantasy_prize_winners filters on it), the owner has a ranking exclusion list (`app_private.public_ranking_exclusions`), staff can ban users, and the account-deletion path and 3-per-day limits exist.
- Attack path: (1) attacker scripts `signUp` against the public Auth endpoint with generated disposable addresses, up to the per-IP limit and rotating IPs. (2) Confirms each email. (3) Each account creates a Fantasy team and joins the sponsored league. (4) The set of accounts shares one real winner.
- Severity: Medium for a prize-bearing challenge (Low for the app as it is today). Effort: M (turn on Turnstile in the dashboard, pass `captchaToken` from the sign-up and reset forms; add a prize-eligibility check on verified phone or one-prize-per-person at payout).

### C12. `/mcp` tools and `trustForwardedHost: true` (Low)
- What it exposes, and to whom: three read-only tools, `get_profile`, `get_fantasy_team`, `list_fixtures` (src/lib/mcp/index.ts:18). The route accepts an OAuth bearer token issued by this project's Supabase Auth (`issuer: https://<project>.supabase.co/auth/v1`, `acceptedAudiences: "authenticated"`). `get_profile` reads `api.my_profile` (username, display name, favourite club, language) for the token's own user only; `get_fantasy_team` the caller's own squad summary; `list_fixtures` calls the public `api.football_upcoming_matches` (src/lib/mcp/tools/*.ts). All data reads run as the caller (the user's token, publishable key), so the database decides, not the tool. Accounts with two-step sign-in get a refusal for their own data (src/lib/mcp/account-read.ts). Unauthenticated calls get "Not authenticated". Because `acceptedAudiences` is `"authenticated"`, an ordinary signed-in browser session token also works here, but only for that user's own data.
- `trustForwardedHost: true` (src/routes/mcp.ts:13 and src/routes/[.well-known]/oauth-protected-resource.ts:14): when set, the library rewrites the request URL host to the first `X-Forwarded-Host` value before building the OAuth `resource`, metadata URL and `WWW-Authenticate` header (node_modules/@lovable.dev/mcp-js/dist/forwarded--h4efJy-.js:24-38). Its own comment says this is safe only behind a proxy that overwrites the header and that an unchecked value "can redirect the advertised resource to an attacker origin".
- Can a forged header alter the metadata? Only if no proxy in front overwrites `X-Forwarded-Host`. The comment says Lovable's web proxy does overwrite it, and the site sits behind Cloudflare. I did not test it (my request budget was spent on C2, and probing with a forged header was outside the 3 allowed requests), so this is code reading only. Limits on the damage even if the header got through: (1) accepted token audiences are the fixed string `authenticated`, not derived from the host (cors-BXcpNLm9.js:495), so a forged host cannot make the server accept a token it should not; (2) responses I could see in the code carry `Cache-Control: no-store` (cors-BXcpNLm9.js:683, 694), so a poisoned reply is not stored for other users; (3) an attacker cannot set headers on a victim's request, so the only person who sees the forged `resource` URL is the attacker. Realistic impact: none found. A forged header would matter only if a CDN or proxy path exists that both forwards it and lets one user's response reach another.
- Severity: Low (informational). Effort: S (one curl with `-H "X-Forwarded-Host: evil.example"` to `/.well-known/oauth-protected-resource`, run by the owner or by me in phase 2, will settle it; if the reply names `evil.example`, set `trustForwardedHost: false`).
- Also from r1 C1: the MCP SDK advisories matter only if this route is used; whether the Supabase OAuth server is enabled in production is still Q4.

### C2. No script-src Content-Security-Policy (FIXED 3: measured; downgraded to Low)
- What: measured on 2026-10-27, the live site sends HSTS (`max-age=31536000; includeSubDomains`), `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: SAMEORIGIN` and `Content-Security-Policy: frame-ancestors 'self'`.
